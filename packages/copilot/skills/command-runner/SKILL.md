# CommandRunner operations

This is **method guidance, not execution permission**. Copilot declares Skill loading; confirm that the installed Skill and referenced guides are available within the approved boundary before terminal use. Do not read outside that boundary. The human grant, exact delegated action, effects, and host permission remain authoritative.

Use only the user-level CLI `node ~/.copilot/skills/command-runner/scripts/cli.mjs` through the delegated terminal tool, **never** a raw project shell command or the internal management interface. Terminal mode is synchronous (`mode: "sync"` if supported); omit the terminal timeout or use `0` only if the tool requires it. Do not override cwd, environment, profile or shell.

## Procedure

1. **Known exact command ID:** directly `inspect` its effective definition if this operation is delegated. Avoid needless `list`.
2. **Unknown ID:** use a delegated `list` with a bounded query and pagination; inspect exact candidates only when authorized. Filtered misses, stale revisions and incomplete pages do not prove absence. An npm script name (possibly containing `:`) is not necessarily a safe command ID.
3. **Before execution:** audit the actual workspace, command definition, arguments, script lifecycle hooks, and all effects. Terminal metadata calls require `observe+execute`. A `run` reads shared execution-cache size metadata and writes new runner-owned logs under `$COPILOT_HOME/command-runner/executions/`. Grant this bounded observation and the current workspace's output-cache `change_local`, plus any intended source/test outputs. Normal `run` never deletes old caches: when the global limit is reached it fails closed with `execution_cache_full`, leaving owner-only cache maintenance separate. For a project-required registered local formatter with approved workspace-local write effects, do not predict every file it may format or add a per-file post-format audit. Preserve the required command, args, scope and order; explicit caps, external and destructive effects still constrain execution.
   Known check-owned outputs outside the workspace (including OS temp files) require a verified, bounded scope in the same approved grant and Card; the shared temp root is not blanket permission. Cleanup/deletion retains `destructive` when applicable; unknown paths or effects block the operation. Report an in-grant Card omission as a delegation gap, not missing human approval.
4. **Execution:** call `run` only for an exact permitted registered ID with validated named arguments. Capture `executionId`, `exitCode`, signal and timeout status. A shortened preview can be completed with separately authorized `output` chunks only if `outputTruncated` is false. If `outputTruncated: true`, the Runner stopped collecting beyond its output limit: lost bytes cannot be recovered by `output`. Treat the execution as incomplete/failed, record that limitation and do not claim verification.
5. **Missing registration:** `workspace.ensure` or `propose` requires delegated registration actions; `propose` creates only a proposal. Before `propose`, investigate the actual command and its scope, inputs, effects (including caches and pre/post scripts), output and success criteria. Write a concrete, evidence-based `description` (20-500 characters); never label an unverified command read-only. `activate` is a separate host/human-approved registry mutation. Never use registration to evade a permission or lookup failure.

## Registered command argv allowlists

Configured project commands have two modes: **Fixed** without an `allow` field, or **Allowlist** with a non-empty array of rule strings. Legacy `arguments` definitions remain valid for existing commands, but cannot be mixed with non-empty `arguments` on an Allowlist command. Builtins retain their separate contracts.

Allowed rules are `--coverage` (flag), `--maxWorkers=value` (scalar), `--config=path` (existing workspace-contained path), and `--runTestsByPath path...` (one or more existing workspace-contained files). Only one `path...` group is supported; `--option=value` and `--option value` both work. Rule order is irrelevant. No bare positional files, unknown or repeated options. These strings describe permissions; they are not shell code.

Worker-facing `run` transports ordered argv as repeated percent-encoded `arg=` parameters. Example: `run test arg=--coverage arg=--runTestsByPath arg=tests%2Fa.test.js`. Encode special characters, whitespace and non-ASCII characters, including apostrophes and parentheses (`encodeURIComponent` alone leaves `!'()*` unescaped; percent-encode those characters as well). Never use terminal shell quotes or interpolation. Builtins/legacy commands still use their original named parameters.

For npm-family scripts, use `propose test description=<encoded-text>` with optional `script`, `packageDir`, and `allow=<percent-encoded-JSON-string-array>`; omit `allow` for Fixed. Existing description-less npm proposals remain accepted for compatibility, but Workers must provide an evidence-based description. For a general **Fixed argv** command, use `propose check definition=<percent-encoded-JSON-object>` containing `description`, a literal `run` string array, `cwd`, and optional bounded `timeoutMs`/`maxOutputBytes`; `arguments` may only be `{}` and `allow` is not supported. Shell/proxy launchers, inline interpreter evaluation, and package managers through this fixed path are rejected; use the package-script path for npm-family scripts. Arbitrary Fixed commands are not sandboxed and may execute changed source/dependencies: audit actual effects before every authorized run. `propose` is inert with respect to the project and registry but writes a bounded proposal file. To update an **existing** command, use `propose.update <id> patch=<percent-encoded-JSON-object>` and specify only fields to change. Supported patches: `description`, `timeoutMs`, `maxOutputBytes`, safe Fixed `run`/`cwd`, and for registered package scripts `script`/`packageDir`/`allow`. Unmentioned settings (including legacy arguments, guards and limits) are retained. `activate <proposal-id>` requires separate Host/human approval, reviews the exact effective definition, and rejects stale concurrent changes. Legacy variable argument schemas cannot be widened through this Worker API; builtins remain immutable. Neither proposing nor activation grants execution authority. Both types require separate human Host approval for `activate`. Never bypass the Hook if interactive approval is unavailable.

## Git read-only builtins

Use an exact, registration-free Git observation built-in rather than proposing a raw project Git shell command. Existing status, diff, log, show, ls-files and branch-info builtins are retained. The additional read-only builtins cover branch listing, blame, grep, merge-base, rev-parse, rev-list, worktree listing, reflog, range-diff and ls-tree. Inspect the known ID for its named schema, and pass URL-encoded `key=value` arguments as usual. For `builtin-git-diff`, `scope=commits base=main target=HEAD comparison=merge-base` compares the merge base to HEAD, whereas `comparison=direct` compares the two tips. No Git branch mutation, arbitrary Git argv, or new execution authority is granted; exact Task Card scope remains in force.

## Git worktree context

Git-verified linked worktrees automatically inherit registered commands from their registered repository root by default. No additional `workspace.ensure` or `workspace.worktrees.enable` operation is needed for an inherited worktree. If `inheritWorktrees: false` is explicitly configured, inheritance is disabled; do not override this setting to circumvent a denial. Registered command definitions are shared while file paths, cwd, execution output, and approval proposals are bounded to the current worktree. A changed branch-local package script still fails its existing script guard. Execution remains subject to exact human authorization and effects.

## Host integration

Runner terminal invocation is not permissionless, even for builtins. Never retry denied commands via shell aliases, disable Hook checks, issue `exit`/`exec`, or guess which tab belongs to the Worker. The current Hook requires synchronous foreground terminal calls; VS Code may retain tabs after they finish. Background auto-disposal is a separate harness-specific experiment and must not be enabled until output/exit code and owner-scoped cleanup are verified.
